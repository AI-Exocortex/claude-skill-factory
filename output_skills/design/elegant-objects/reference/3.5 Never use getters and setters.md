# Elegant Objects - Object-Oriented Design Patterns

## EOO.3.5 - Never use getters and setters

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.3.5:1 - Problem frame

Encapsulation makes an object a black box with behavior, not a transparent bag of values managed by its clients.

### EOO.3.5:2 - Problem

Getter and setter prefixes expose internal storage as an API, turning a class into a data structure and shifting domain operations back into external procedural code.

### EOO.3.5:3 - Forces

- Accessors integrate easily with frameworks and tools.
- Behavior-oriented operations protect representation but require stronger domain modeling.

### EOO.3.5:4 - Solution

Do not expose property access through `getX` or `setX`. Ask an object for a meaningful result such as `dollars()`, or create a new object for a changed state. Keep representation and its transformations inside the object.

#### EOO.3.5:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Cash {
    private int cents;

    int getCents() {
        return cents;
    }

    void setCents(int cents) {
        this.cents = cents;
    }
}
```

**Good**

```java
final class Cash {
    private final int cents;

    Cash(int cents) {
        this.cents = cents;
    }

    Cash plus(Cash other) {
        return new Cash(cents + other.cents);
    }

    int cents() {
        return cents;
    }
}
```

### EOO.3.5:5 - Archetypal Grounding

**System:** `Cash.dollars()` answers a domain question; `getDollars()` tells the client to retrieve a presumed field.  
**Episteme:** the name determines whether a client reads a capability or an implementation assumption.

### EOO.3.5:6 - Bias-Annotation

The **Onto/Epist** and **Arch** lenses favor opaque objects. The **Prag** lens acknowledges serialization, UI binding, and legacy framework boundaries, which should be isolated rather than treated as the domain model.

### EOO.3.5:7 - Conformance Checklist

- Remove public setters from domain objects.
- Rename raw-access getters as domain queries only when they do not promise storage.
- Move operations on exposed data into the owning object.

### EOO.3.5:8 - Common Anti-Patterns and How to Avoid Them

- **Accessor with validation:** validation does not turn direct state access into behavior.
- **Anemic model:** do not place all domain logic in external services while objects expose fields.

### EOO.3.5:9 - Consequences

Representation can evolve without clients managing it directly. Boundaries that require field-shaped data need explicit translation objects or adapters.

### EOO.3.5:10 - Rationale

Data structures are transparent carriers; objects are active role bearers. Getter/setter APIs erase that distinction and spread responsibility for state transitions across clients.

### EOO.3.5:11 - SoTA-Echoing

Not applicable. This note preserves the supplied source’s categorical view; it does not deny the existence of framework-driven data transfer objects.
