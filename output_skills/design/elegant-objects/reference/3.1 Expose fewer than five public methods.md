# Elegant Objects - Object-Oriented Design Patterns

## EOO.3.1 - Expose fewer than five public methods

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.3.1:1 - Problem frame

The public methods of a class are the capability surface that every client and maintainer must understand.

### EOO.3.1:2 - Problem

A wide surface usually combines several responsibilities. It makes object behavior harder to name, test, keep coherent, and evolve without breaking consumers.

### EOO.3.1:3 - Forces

- A broad API can be convenient for immediate callers.
- A small API limits cognitive load and reveals whether an object has one role.

### EOO.3.1:4 - Solution

Keep an object’s public interface below roughly five methods. If it exceeds that bound, identify cohesive groups and split or compose objects around their distinct roles.

#### EOO.3.1:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Report {
    void load() {}
    void validate() {}
    void calculate() {}
    void render() {}
    void email() {}
    void archive() {}
}
```

**Good**

```java
final class RenderedReport {
    private final ReportData data;

    RenderedReport(ReportData data) {
        this.data = data;
    }

    String html() {
        return "<p>" + data + "</p>";
    }
}
```

### EOO.3.1:5 - Archetypal Grounding

**System:** a class with `read`, `write`, `validate`, `send`, `cache`, and `report` combines several roles; separate objects can own those capabilities.  
**Episteme:** the method list is an inspectable signature of the object’s declared responsibility.

### EOO.3.1:6 - Bias-Annotation

The **Did** and **Arch** lenses favor small capability surfaces. The **Prag** lens limits the number: five is a diagnostic threshold, not a substitute for cohesion analysis.

### EOO.3.1:7 - Conformance Checklist

- Count public methods on each concrete role.
- Describe its single responsibility in one sentence.
- Split unrelated method clusters by client need.

### EOO.3.1:8 - Common Anti-Patterns and How to Avoid Them

- **Private-method gaming:** hiding public behavior without changing responsibility does not improve cohesion.
- **Single-method fragmentation:** do not split methods that form one meaningful capability.

### EOO.3.1:9 - Consequences

Objects become easier to learn, test, and substitute. Clients may need more composition, which is a visible cost rather than hidden breadth.

### EOO.3.1:10 - Rationale

A small interface reduces the number of relationships that must remain harmonious. The count is useful because it makes a vague design concern observable.
