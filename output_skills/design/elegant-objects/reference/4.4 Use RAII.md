# Elegant Objects - Object-Oriented Design Patterns

## EOO.4.4 - Use RAII

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.4.4:1 - Problem frame

Files, streams, and connections need timely release; garbage collection alone does not establish a reliable lifetime for external resources.

### EOO.4.4:2 - Problem

Manual acquisition and cleanup can diverge across control-flow paths, leaving a resource held after the work that needed it has finished.

### EOO.4.4:3 - Forces

- Deterministic cleanup simplifies resource ownership.
- Some runtimes do not have deterministic destruction and require an explicit scoped protocol.

### EOO.4.4:4 - Solution

Acquire a resource when constructing its owning object and release it when that object leaves its defined lifetime. Use RAII destructors in C++; in Java, use `AutoCloseable` with try-with-resources so `close()` is invoked at scope exit.

#### EOO.4.4:4.1 - Bad vs. good Java examples

**Bad**

```java
void print(java.nio.file.Path path) throws java.io.IOException {
    java.io.InputStream input = java.nio.file.Files.newInputStream(path);
    System.out.println(input.read());
    // The stream is not closed if reading fails.
}
```

**Good**

```java
void print(java.nio.file.Path path) throws java.io.IOException {
    try (java.io.InputStream input =
             java.nio.file.Files.newInputStream(path)) {
        System.out.println(input.read());
    }
}
```

### EOO.4.4:5 - Archetypal Grounding

**System:** `Text` opens a file in construction and closes it in destruction; `try (Text t = …)` gives the Java equivalent scope-bound release.  
**Episteme:** the lifetime construct is evidence of who owns the resource and when its release is guaranteed.

### EOO.4.4:6 - Bias-Annotation

The **Prag**, **Gov**, and **Trust** lenses favor deterministic ownership. The exact mechanism depends on language runtime and must not be inferred from garbage-collection behavior.

### EOO.4.4:7 - Conformance Checklist

- Identify an owner for each external resource.
- Bind acquisition and release to a lexical or explicit scope.
- Test exceptional paths for guaranteed release.

### EOO.4.4:8 - Common Anti-Patterns and How to Avoid Them

- **Garbage-collector cleanup:** do not use finalization timing as a resource protocol.
- **Unowned handle:** avoid passing a resource without an explicit close responsibility.

### EOO.4.4:9 - Consequences

Resource release becomes reliable and locally auditable. APIs must make ownership and close semantics clear, especially when resources are transferred.

### EOO.4.4:10 - Rationale

The resource’s physical lifetime is part of the work, not incidental memory management. Binding it to object scope gives a concrete, checkable relation between acquisition, use, and cleanup.
