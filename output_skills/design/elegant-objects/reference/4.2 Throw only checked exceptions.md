# Elegant Objects - Object-Oriented Design Patterns

## EOO.4.2 - Throw only checked exceptions

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.4.2:1 - Problem frame

Failure is part of the behavior a caller must understand. A method contract that conceals possible failures provides incomplete evidence about its outcome.

### EOO.4.2:2 - Problem

Unchecked exceptions hide failure paths from method signatures; catching to return a fallback or merely log loses context and turns exceptions into control flow.

### EOO.4.2:3 - Forces

- Unchecked exceptions keep signatures short.
- Checked, chained exceptions expose risk and provenance but can propagate through many layers.

### EOO.4.2:4 - Solution

Declare checked exceptions for recoverable-by-caller failure paths. Catch only when a layer can resolve the problem; otherwise chain the original exception into a richer context and rethrow. Recover once, at an application entry point, and move cross-cutting retry logic into an aspect or decorator.

#### EOO.4.2:4.1 - Bad vs. good Java examples

**Bad**

```java
int length(java.io.File file) {
    try {
        return java.nio.file.Files.readAllBytes(file.toPath()).length;
    } catch (java.io.IOException failure) {
        throw new IllegalStateException("Cannot read file");
    }
}
```

**Good**

```java
int length(java.io.File file) throws DocumentFailure {
    try {
        return java.nio.file.Files.readAllBytes(file.toPath()).length;
    } catch (java.io.IOException failure) {
        throw new DocumentFailure("Cannot read " + file, failure);
    }
}

final class DocumentFailure extends Exception {
    DocumentFailure(String message, Throwable cause) {
        super(message, cause);
    }
}
```

### EOO.4.2:5 - Archetypal Grounding

**System:** a file-length operation throws a chained exception from filesystem failure through document context to a user-facing boundary.  
**Episteme:** the exception chain is a provenance path explaining why the normal result is unavailable.

### EOO.4.2:6 - Bias-Annotation

The **Trust**, **Gov**, and **Prag** lenses favor visible failure provenance. The pattern assumes a language with checked exceptions; other languages require an equivalent explicit error carrier.

### EOO.4.2:7 - Conformance Checklist

- Make declared failure cases visible in the contract.
- Preserve the original cause whenever adding context.
- Restrict recovery to a boundary that owns the resolution decision.

### EOO.4.2:8 - Common Anti-Patterns and How to Avoid Them

- **Catch-and-log:** rethrow with context unless the catch resolves the condition.
- **Exception as branch:** model expected alternatives in the normal contract.

### EOO.4.2:9 - Consequences

Failure paths become explicit and diagnosable. Signatures and composition can become more verbose, which records a real obligation rather than incidental syntax.

### EOO.4.2:10 - Rationale

Chained exceptions retain evidence as failure crosses abstraction boundaries. A single recovery owner prevents multiple layers from independently deciding that an error is harmless.

Not applicable. The note preserves the source’s Java-centric exception position without asserting its direct applicability to languages without checked exceptions.
