# Elegant Objects - Object-Oriented Design Patterns

## EOO.2.4 - Choose method names carefully

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.2.4:1 - Problem frame

A method name should reveal whether a client is requesting a result or asking an object to change the represented world.

### EOO.2.4:2 - Problem

Methods that both mutate and return a result conflate two roles; verb names for queries and noun names for commands obscure that ambiguity.

### EOO.2.4:3 - Forces

- Combined methods can look convenient at a call site.
- A clear command/query distinction makes effects and expectations readable.

### EOO.2.4:4 - Solution

Name builders (methods that return objects) with nouns, such as `content()` or `sum()`. Name manipulators (methods that change the represented world) with verbs and return `void`, such as `paint()`. Use adjectives for Boolean builders such as `empty()`.

#### EOO.2.4:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Document {
    int save(java.io.InputStream content) {
        // Writes content and returns the byte count.
        return 42;
    }
}
```

**Good**

```java
final class Output {
    void write(java.io.InputStream content) {
        // Writes content.
    }

    int bytesWritten() {
        return 42;
    }
}
```

### EOO.2.4:5 - Archetypal Grounding

**System:** `Document.output()` yields an `OutputPipe`; `OutputPipe.write(content)` performs the mutation, while `bytes()` reports a separate result.  
**Episteme:** name and return type jointly state the method’s role.

### EOO.2.4:6 - Bias-Annotation

The **Did** lens favors a readable grammatical convention, while **Arch** favors separated responsibilities. The **Prag** lens recognizes language and framework conventions that may differ.

### EOO.2.4:7 - Conformance Checklist

- Classify each public method as builder or manipulator.
- Give builders noun/adjective names and meaningful return types.
- Give manipulators verb names and no return value.

### EOO.2.4:8 - Common Anti-Patterns and How to Avoid Them

- **`save()` returning bytes:** separate saving from reporting bytes written.
- **`getX()` query names:** use the requested value or capability as the name.

### EOO.2.4:9 - Consequences

Call sites communicate intent more clearly and mixed responsibilities surface early. A strict convention may require decomposing familiar APIs.

### EOO.2.4:10 - Rationale

The naming rule turns a semantic distinction into a local, reviewable cue. It discourages a method from masquerading as both a request and a procedure.

### EOO.2.4:11 - SoTA-Echoing

Not applicable. The formulation documents the source’s convention rather than a universal naming standard.
