# Elegant Objects - Object-Oriented Design Patterns

## EOO.2.3 - Always use interfaces

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.2.3:1 - Problem frame

Clients need a stable description of the capability they consume, independent of a particular implementation.

### EOO.2.3:2 - Problem

When clients depend directly on concrete classes, replacement and testing require knowledge of implementation details rather than the service contract.

### EOO.2.3:3 - Forces

- Concrete types are simple to instantiate and discover.
- Interface contracts add declarations but make dependencies explicit and substitutable.

### EOO.2.3:4 - Solution

Define and depend on an interface for public behavior. Have concrete classes implement that contract, and ensure public methods are traceable to at least one interface.

#### EOO.2.3:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Employee {
    private final DefaultCash salary;

    Employee(DefaultCash salary) {
        this.salary = salary;
    }
}
```

**Good**

```java
interface Cash {
    int cents();
}

final class Employee {
    private final Cash salary;

    Employee(Cash salary) {
        this.salary = salary;
    }
}
```

### EOO.2.3:5 - Archetypal Grounding

**System:** `Employee` depends on `Cash`, while `DefaultCash` supplies one implementation; either implementation can change without changing `Employee`.  
**Episteme:** the interface is the published capability description shared by consumers and providers.

### EOO.2.3:6 - Bias-Annotation

The **Arch** lens favors replaceable dependencies; the **Gov** lens favors explicit contracts. The **Prag** lens warns against premature interfaces with only accidental variation.

### EOO.2.3:7 - Conformance Checklist

- Name the capability consumed by each client.
- Depend on its interface at the boundary.
- Verify that implementations can be replaced without client changes.

### EOO.2.3:8 - Common Anti-Patterns and How to Avoid Them

- **Marker interface:** do not create an interface that names no usable contract.
- **Implementation-shaped contract:** avoid leaking concrete storage or lifecycle details into it.

### EOO.2.3:9 - Consequences

The software gains stable, testable seams and explicit coupling. More interfaces can make navigation noisier when variation is imaginary.

### EOO.2.3:10 - Rationale

An interface gives an object’s offered role a durable carrier. It makes the dependency a declared relation instead of an inference from a concrete class.

### EOO.2.3:11 - SoTA-Echoing

Not applicable. This note is a study formulation of the supplied source and does not claim that every contemporary codebase should introduce an interface.
