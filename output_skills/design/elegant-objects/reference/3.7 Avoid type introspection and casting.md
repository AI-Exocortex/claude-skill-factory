# Elegant Objects - Object-Oriented Design Patterns

## EOO.3.7 - Avoid type introspection and casting

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.3.7:1 - Problem frame

Polymorphic objects promise behavior through their declared contracts; clients should not need to inspect undisclosed concrete identities to decide how to act.

### EOO.3.7:2 - Problem

`instanceof`, reflection, and casts create hidden dependencies on concrete types and force callers to branch on implementation knowledge.

### EOO.3.7:3 - Forces

- Type inspection can enable a local optimization.
- Overloads, polymorphism, and separate roles make dependencies explicit but may require redesign.

### EOO.3.7:4 - Solution

Avoid type introspection and casting in ordinary domain behavior. Express distinct contracts as overloads or separate methods; let each object fulfill the behavior it already promised.

#### EOO.3.7:4.1 - Bad vs. good Java examples

**Bad**

```java
int sizeOf(Iterable<?> items) {
    if (items instanceof java.util.Collection<?> collection) {
        return collection.size();
    }
    int size = 0;
    for (Object ignored : items) {
        size++;
    }
    return size;
}
```

**Good**

```java
int sizeOf(java.util.Collection<?> items) {
    return items.size();
}

int sizeOf(Iterable<?> items) {
    int size = 0;
    for (Object ignored : items) {
        size++;
    }
    return size;
}
```

### EOO.3.7:5 - Archetypal Grounding

**System:** provide `size(Collection)` and `size(Iterable)` rather than inspect whether an `Iterable` happens to be a `Collection`.  
**Episteme:** the signatures publish the two supported input roles instead of concealing an optimization branch.

### EOO.3.7:6 - Bias-Annotation

The **Arch** and **Did** lenses favor explicit contracts. The **Prag** lens recognizes reflection-heavy frameworks and interoperability code as boundary cases that require isolated, audited exceptions.

### EOO.3.7:7 - Conformance Checklist

- Locate casts, reflection, and run-time type branches.
- Replace implementation-sensitive paths with declared roles or overloads.
- Document any boundary exception and keep it local.

### EOO.3.7:8 - Common Anti-Patterns and How to Avoid Them

- **Optimization leak:** do not expose a hidden type preference through one general signature.
- **Speculative cast:** do not make an object promise a role it has not declared.

### EOO.3.7:9 - Consequences

Clients rely on contracts instead of concrete knowledge. Some performance paths need explicit alternate interfaces and measured justification.

### EOO.3.7:10 - Rationale

Type introspection changes a role-based relation into an implementation-based relation. Explicit signatures preserve the evidence chain of what the client may legitimately expect.
