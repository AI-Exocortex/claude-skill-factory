# Elegant Objects - Object-Oriented Design Patterns

## EOO.2.1 - Encapsulate as little as possible

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.2.1:1 - Problem frame

Each encapsulated collaborator is part of an object’s identity and expands the behavioral surface a reader must understand.

### EOO.2.1:2 - Problem

A class that holds many collaborators coordinates too many concerns and becomes difficult to name, test, and change safely.

### EOO.2.1:3 - Forces

- Real tasks may need many dependencies.
- A compact object boundary improves local reasoning and makes composition visible.

### EOO.2.1:4 - Solution

Aim to encapsulate four objects or fewer. Treat a larger dependency set as a refactoring signal: split the object into smaller collaborators that can be composed into a higher-level whole.

#### EOO.2.1:4.1 - Bad vs. good Java examples

**Bad**

```java
final class OrderService {
    OrderService(Repository repo, Clock clock, Mailer mailer,
                 Auditor audit, Pricing pricing) {
        // Five collaborators, several responsibilities.
    }
}
```

**Good**

```java
final class PricedOrder {
    private final Order order;
    private final Pricing pricing;

    PricedOrder(Order order, Pricing pricing) {
        this.order = order;
        this.pricing = pricing;
    }

    Money total() {
        return pricing.price(order);
    }
}
```

### EOO.2.1:5 - Archetypal Grounding

**System:** an order-processing class holding storage, clock, pricing, mail, audit, policy, and logging is a coordination aggregate rather than one focused object.  
**Episteme:** the dependency list is evidence about the object’s scope.

### EOO.2.1:6 - Bias-Annotation

The **Arch** and **Did** lenses favor a small dependency surface. The **Prag** lens qualifies the numeric limit: four is a heuristic, not a measured universal threshold.

### EOO.2.1:7 - Conformance Checklist

- Count encapsulated production collaborators.
- Explain the role of each in one sentence.
- Refactor unexplained clusters into named objects.

### EOO.2.1:8 - Common Anti-Patterns and How to Avoid Them

- **Dependency camouflage:** moving collaborators to globals or service locators does not reduce coupling.
- **Numerology:** do not split a coherent object merely to meet the number four.

### EOO.2.1:9 - Consequences

Objects become smaller and more composable. The system may contain more classes, so names and interfaces must carry more of the explanatory load.

### EOO.2.1:10 - Rationale

Limiting the immediate part-whole relation controls the local complexity of the holon. The target is understandable composition, not a low field count by itself.
