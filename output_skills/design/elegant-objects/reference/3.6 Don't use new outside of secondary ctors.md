# Elegant Objects - Object-Oriented Design Patterns

## EOO.3.6 - Don't use new outside of secondary ctors

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.3.6:1 - Problem frame

An object should use collaborators that its client has chosen; creating those collaborators during behavior hard-codes a hidden dependency.

### EOO.3.6:2 - Problem

`new` in a method or primary constructor couples the object to a concrete implementation, makes tests reach external systems, and mixes composition with execution.

### EOO.3.6:3 - Forces

- Direct construction is concise and local.
- Constructor injection exposes configuration and permits replacement, but makes object graphs explicit.

### EOO.3.6:4 - Solution

Use `new` only in secondary constructors, where a convenient default can be composed before delegating. Supply every production collaborator to the primary constructor and never construct one inside ordinary methods.

#### EOO.3.6:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Cash {
    int euros() {
        return new LiveExchange().rate("USD", "EUR");
    }
}
```

**Good**

```java
final class Cash {
    private final Exchange exchange;

    Cash(Exchange exchange) {
        this.exchange = exchange;
    }

    int euros() {
        return exchange.rate("USD", "EUR");
    }
}
```

### EOO.3.6:5 - Archetypal Grounding

**System:** `Cash(5, new FakeExchange())` lets a caller select the exchange; `Cash` does not create a live `Exchange` during `euro()`.  
**Episteme:** constructor arguments are visible evidence of the collaboration required for behavior.

### EOO.3.6:6 - Bias-Annotation

The **Arch**, **Prag**, and **Trust** lenses favor dependency injection. The pattern can make wiring verbose, which is a useful signal about the composed system rather than a reason to hide dependencies.

### EOO.3.6:7 - Conformance Checklist

- Search production methods and primary constructors for direct construction.
- Move required collaborators into primary-constructor parameters.
- Limit default construction to secondary-constructor delegation.

### EOO.3.6:8 - Common Anti-Patterns and How to Avoid Them

- **Service locator:** global lookup still hides the dependency.
- **Test-only injection:** production composition must also use the explicit contract.

### EOO.3.6:9 - Consequences

Tests can control dependencies and implementations are replaceable. Composition roots become richer and deserve their own clear design.

### EOO.3.6:10 - Rationale

The rule separates two kinds of work: constructing an object graph and executing behavior in that graph. It turns otherwise hidden coupling into a declared role assignment.

### EOO.3.6:11 - SoTA-Echoing

Not applicable. This is a source-derived dependency-discipline rule, not a claim that all direct construction in contemporary software is invalid.
