# Elegant Objects - Object-Oriented Design Patterns

## EOO.4.1 - Never return NULL

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.4.1:1 - Problem frame

When a method declares that it returns an object, its client needs a result that can be used according to that object’s contract.

### EOO.4.1:2 - Problem

Returning `NULL` makes every client distrust the result and either branch defensively or fail far from the original cause.

### EOO.4.1:3 - Forces

- `NULL` is an inexpensive local absence marker.
- Exceptions, empty collections, and null objects preserve a usable contract but require an explicit semantic decision.

### EOO.4.1:4 - Solution

Never return `NULL`. Throw an exception for an unavailable required result, return an empty collection for a plural query, or return a role-valid null object where absence itself has useful behavior. Prefer fail-fast propagation over silently fabricated scalar values.

#### EOO.4.1:4.1 - Bad vs. good Java examples

**Bad**

```java
User user(String name) {
    return database.contains(name) ? database.get(name) : null;
}
```

**Good**

```java
User user(String name) throws UnknownUser {
    if (!database.contains(name)) {
        throw new UnknownUser(name);
    }
    return database.get(name);
}
```

### EOO.4.1:5 - Archetypal Grounding

**System:** `users(name)` returns an empty collection when no matching user exists; a single-user query can signal a missing required user explicitly.  
**Episteme:** the return type remains a reliable statement of what a caller can do next.

### EOO.4.1:6 - Bias-Annotation

The **Trust** and **Prag** lenses favor failures close to their cause. The pattern strongly prefers fail-fast behavior and must be reconciled with an application’s user-facing recovery policy.

### EOO.4.1:7 - Conformance Checklist

- Search every object-returning method for nullable paths.
- Classify absence as exceptional, plural-empty, or role-valid.
- Test the selected result behavior without caller null checks.

### EOO.4.1:8 - Common Anti-Patterns and How to Avoid Them

- **Sentinel scalar:** `-1` or `0` merely disguises `NULL` when not a valid domain value.
- **Catch and continue:** do not hide the causal failure in a plausible result.

### EOO.4.1:9 - Consequences

Clients can trust return contracts and error causes remain near their origin. The design needs deliberate absence semantics rather than one universal marker.

### EOO.4.1:10 - Rationale

A method that returns a non-object after promising an object breaks the object relation. Explicit alternatives maintain the correspondence between signature, result, and client behavior.
