# Elegant Objects - Object-Oriented Design Patterns

## EOO.3.3 - Never accept NULL arguments

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.3.3:1 - Problem frame

A parameter contract should state the object or value an operation needs; absence is a distinct semantic case, not an untyped placeholder.

### EOO.3.3:2 - Problem

Accepting `NULL` overloads a parameter with two meanings and pushes every recipient toward defensive branching. The real contract is hidden from the type and signature.

### EOO.3.3:3 - Forces

- One nullable method can look compact.
- Separate methods or a null object make cases explicit but increase the number of types or signatures.

### EOO.3.3:4 - Solution

Do not accept `NULL`. Express absence as a separate operation, an empty collection where the contract is plural, or a meaningful null object such as `AnyFile` that implements the required role.

#### EOO.3.3:4.1 - Bad vs. good Java examples

**Bad**

```java
java.util.List<java.io.File> files(String mask) {
    if (mask == null) {
        return allFiles();
    }
    return matchingFiles(mask);
}
```

**Good**

```java
java.util.List<java.io.File> files() {
    return allFiles();
}

java.util.List<java.io.File> filesMatching(String mask) {
    return matchingFiles(mask);
}
```

### EOO.3.3:5 - Archetypal Grounding

**System:** replace `find(NULL)` with `findAll()` or pass an `AnyFile` matcher whose behavior represents unfiltered selection.  
**Episteme:** the signature announces each admissible input shape instead of making one case implicit.

### EOO.3.3:6 - Bias-Annotation

The **Arch** and **Trust** lenses favor total, explicit contracts. The **Prag** lens recognizes that interoperability boundaries may use nullable values and need adapters at that boundary.

### EOO.3.3:7 - Conformance Checklist

- Reject or adapt nullable input at the boundary.
- Name the absent-case behavior explicitly.
- Ensure clients need no null check before a normal call.

### EOO.3.3:8 - Common Anti-Patterns and How to Avoid Them

- **Sentinel scalar:** replacing `NULL` with `-1` preserves the hidden second meaning.
- **Null object without contract:** ensure the substitute obeys the same interface meaningfully.

### EOO.3.3:9 - Consequences

Call sites and contracts become more explicit. APIs may grow additional named cases, which is preferable to untyped ambiguity.

### EOO.3.3:10 - Rationale

An object either fulfills a role or it does not. Treating absence as a role-bearing value or a separate operation preserves the distinction in the signature.
