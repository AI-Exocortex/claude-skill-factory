# Elegant Objects - Object-Oriented Design Patterns

## EOO.2.9 - Keep interfaces short; use smarts

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.2.9:1 - Problem frame

An interface is a client-facing capability boundary; every method enlarges the obligation an implementer and user must understand.

### EOO.2.9:2 - Problem

Large interfaces force classes to expose broad, weakly related behavior and make small implementations unnecessarily complex.

### EOO.2.9:3 - Forces

- Broad interfaces can appear convenient as one-stop APIs.
- Small interfaces improve substitutability but require composition and careful discovery.

### EOO.2.9:4 - Solution

Keep interfaces narrow, ideally with a small number of coherent methods. Put coordination or derived behavior into smart implementations and decorators rather than enlarging a common contract.

#### EOO.2.9:4.1 - Bad vs. good Java examples

**Bad**

```java
interface Document {
    byte[] content();
    int length();
    void save(byte[] content);
    void encrypt(Key key);
    void publish();
}
```

**Good**

```java
interface Content {
    byte[] bytes();
}

final class SizedContent implements Content {
    private final Content origin;

    SizedContent(Content origin) {
        this.origin = origin;
    }

    int length() {
        return origin.bytes().length;
    }

    public byte[] bytes() {
        return origin.bytes();
    }
}
```

### EOO.2.9:5 - Archetypal Grounding

**System:** an `Exchange` interface can state one rate capability while a decorator adds caching or validation without changing that contract.  
**Episteme:** the interface declares only the behavior a consumer may rely on.

### EOO.2.9:6 - Bias-Annotation

The **Arch** lens favors focused contracts and the **Did** lens favors comprehensibility. The **Prag** lens treats any numeric method threshold as a heuristic.

### EOO.2.9:7 - Conformance Checklist

- Explain one client role served by the interface.
- Split unrelated method groups into separate contracts.
- Add behavior through implementations or decorators where appropriate.

### EOO.2.9:8 - Common Anti-Patterns and How to Avoid Them

- **Kitchen-sink interface:** divide it by coherent client need.
- **Fragmentation without purpose:** do not create single-method interfaces solely to reduce a count.

### EOO.2.9:9 - Consequences

Implementations become easier to substitute and test. Clients may compose several roles instead of receiving one broad object.

### EOO.2.9:10 - Rationale

A narrow signature makes a role explicit and protects clients from accidental implementation capabilities. Composition can aggregate focused roles without declaring them as one inseparable contract.
