# Elegant Objects - Object-Oriented Design Patterns

## EOO.1.2 - Make one constructor primary

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.1.2:1 - Problem frame

An object may accept equivalent inputs in several representations, while its internal state must be initialized consistently.

### EOO.1.2:2 - Problem

When every constructor initializes fields independently, validation and conversion logic are duplicated. Subsequent changes create divergent initialization paths.

### EOO.1.2:3 - Forces

- Multiple construction forms make a class convenient for clients.
- Multiple state-writing locations make invariants difficult to maintain.

### EOO.1.2:4 - Solution

Choose one primary constructor that performs all field initialization. Make secondary constructors parse, convert, or adapt their arguments and delegate to the primary constructor. Keep the primary constructor visibly last where local conventions permit.

#### EOO.1.2:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Cash {
    private final int cents;

    Cash(String text) {
        this.cents = Integer.parseInt(text);
    }

    Cash(double dollars) {
        this.cents = (int) (dollars * 100);
    }
}
```

**Good**

```java
final class Cash {
    private final int cents;

    Cash(String text) {
        this(Integer.parseInt(text));
    }

    Cash(double dollars) {
        this((int) (dollars * 100));
    }

    Cash(int cents) {
        this.cents = cents;
    }
}
```

### EOO.1.2:5 - Archetypal Grounding

**System:** `Cash(String)`, `Cash(float)`, and `Cash(int)` all create the same cash object; only `Cash(int)` assigns `dollars`.  
**Episteme:** the constructor family is a small method description for normalizing several representations into one state model.

### EOO.1.2:6 - Bias-Annotation

The pattern favors **Arch** and **Prag** lenses: it centralizes invariants and reduces duplicated code. It assumes constructor overloading or an equivalent dispatch mechanism is available.

### EOO.1.2:7 - Conformance Checklist

- Identify exactly one constructor that writes each initialized field.
- Delegate every alternate construction path to it.
- Put shared validation at that single state-writing point.

### EOO.1.2:8 - Common Anti-Patterns and How to Avoid Them

- **Parallel constructors:** do not copy validation into every overload.
- **Constructor branching without a core path:** normalize inputs first, then delegate.

### EOO.1.2:9 - Consequences

Clients gain flexible construction; maintainers gain one place to inspect initialization. The primary constructor can become overburdened if the object itself lacks cohesion.

### EOO.1.2:10 - Rationale

Initialization is an invariant-establishing act. A single canonical path makes the invariant auditable and reduces the number of behaviors that must change together.
