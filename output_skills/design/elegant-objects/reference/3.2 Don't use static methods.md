# Elegant Objects - Object-Oriented Design Patterns

## EOO.3.2 - Don't use static methods

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.3.2:1 - Problem frame

Object composition relies on instances carrying explicit collaborators and interacting through their contracts.

### EOO.3.2:2 - Problem

Static methods are called without an object relationship and encourage imperative control flow, global utility classes, and hidden dependencies that cannot be substituted.

### EOO.3.2:3 - Forces

- Static helpers are concise and familiar.
- Instance collaborators make dependencies explicit and enable decorative composition.

### EOO.3.2:4 - Solution

Represent behavior with objects rather than static procedures. Replace `Math.max(a,b)` with an object such as `Max(a,b)` that implements the needed value contract; build larger behavior by composing decorators around instances.

#### EOO.3.2:4.1 - Bad vs. good Java examples

**Bad**

```java
int maximum = Math.max(left, right);
```

**Good**

```java
final class Maximum {
    private final int left;
    private final int right;

    Maximum(int left, int right) {
        this.left = left;
        this.right = right;
    }

    int value() {
        return left > right ? left : right;
    }
}

int maximum = new Maximum(left, right).value();
```

### EOO.3.2:5 - Archetypal Grounding

**System:** `Sorted(Unique(Capitalized(FileNames(dir))))` describes a composed value without issuing a sequence of static commands.  
**Episteme:** the expression describes the object graph and exposes its dependencies as carriers.

### EOO.3.2:6 - Bias-Annotation

The **Onto/Epist** and **Arch** lenses favor object relationships over global procedures. The **Prag** lens recognizes that many languages and frameworks expose static functions; this is the source’s strict design ideal.

### EOO.3.2:7 - Conformance Checklist

- Locate static calls in domain behavior.
- Replace each with an injected or composed object where a capability is consumed.
- Keep shared behavior behind an explicit interface.

### EOO.3.2:8 - Common Anti-Patterns and How to Avoid Them

- **Utility-class migration:** moving static methods to an empty service class changes no dependency structure.
- **Singleton substitute:** do not exchange one global access path for another.

### EOO.3.2:9 - Consequences

Dependencies become visible and composable. Construction code becomes more explicit, and simple mathematical operations may receive more types than conventional code expects.

### EOO.3.2:10 - Rationale

Static calls erase the holder of a role. Instance composition keeps the relationship between a capability, its context, and its implementation available for inspection and replacement.
