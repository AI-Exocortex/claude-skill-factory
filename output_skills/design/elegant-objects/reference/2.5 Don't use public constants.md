# Elegant Objects - Object-Oriented Design Patterns

## EOO.2.5 - Don't use public constants

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.2.5:1 - Problem frame

A public constant exposes raw shared data without the behavior and context that give it meaning.

### EOO.2.5:2 - Problem

Clients couple to a global value such as `Constants.CRLF`; changing it can alter unrelated behavior, while its semantic role remains distributed among callers.

### EOO.2.5:3 - Forces

- Constants make repeated literals concise.
- Semantic objects make the transformation explicit but add classes and composition.

### EOO.2.5:4 - Solution

Keep private constants local to an implementation. For cross-object reuse, replace a public constant with an object that owns the related behavior, such as `CRLFString`, and pass or compose that object where needed.

#### EOO.2.5:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Constants {
    public static final String CRLF = "\r\n";
}

out.write(text + Constants.CRLF);
```

**Good**

```java
final class CrlfLine {
    private final String text;

    CrlfLine(String text) {
        this.text = text;
    }

    String value() {
        return text + "\r\n";
    }
}

out.write(new CrlfLine(text).value());
```

### EOO.2.5:5 - Archetypal Grounding

**System:** `CRLFString` takes a source string and returns a line-terminated representation; it encodes both the value and its intended operation.  
**Episteme:** the class localizes the meaning that a global literal cannot carry.

### EOO.2.5:6 - Bias-Annotation

The **Arch** lens favors local cohesion and the **Onto/Epist** lens favors semantic carriers. The **Prag** lens notes that language-level constants and protocols can be appropriate when their meaning is genuinely stable and universal.

### EOO.2.5:7 - Conformance Checklist

- Keep implementation literals private.
- Identify public constants used outside their defining class.
- Replace each behavior-bearing shared value with a named collaborator.

### EOO.2.5:8 - Common Anti-Patterns and How to Avoid Them

- **Constants god class:** do not centralize unrelated raw values in one global namespace.
- **Wrapper without behavior:** give the replacement object a clear operation or constraint.

### EOO.2.5:9 - Consequences

Shared meaning becomes localized and substitutions become possible. The design increases the number of small types and requires useful names.

### EOO.2.5:10 - Rationale

Raw data has no self-description of the role it plays. An object can carry both the value and the operation that makes the value meaningful in a bounded context.
