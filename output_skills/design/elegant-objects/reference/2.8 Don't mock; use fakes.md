# Elegant Objects - Object-Oriented Design Patterns

## EOO.2.8 - Don't mock; use fakes

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.2.8:1 - Problem frame

Tests need a controllable replacement for external systems while preserving a client’s relationship to the real interface.

### EOO.2.8:2 - Problem

Interaction mocks couple tests to an implementation’s call sequence. They can reject valid refactorings even when observable behavior has not changed.

### EOO.2.8:3 - Forces

- Mocks are fast to generate and can specify interactions precisely.
- Fakes take more effort but can provide reusable, behaviorally meaningful environments.

### EOO.2.8:4 - Solution

Create a fake implementation of the same interface as the production dependency. Make it behave like a small local version of the external system and use it in tests through normal composition.

#### EOO.2.8:4.1 - Bad vs. good Java examples

**Bad**

```java
Exchange exchange = org.mockito.Mockito.mock(Exchange.class);
org.mockito.Mockito.when(exchange.rate("USD", "EUR"))
    .thenReturn(92);

assertEquals(92, new Cash(100, exchange).euros());
```

**Good**

```java
final class FakeExchange implements Exchange {
    public int rate(String from, String to) {
        return from.equals("USD") && to.equals("EUR") ? 92 : 0;
    }
}

assertEquals(92, new Cash(100, new FakeExchange()).euros());
```

### EOO.2.8:5 - Archetypal Grounding

**System:** `FakeExchange` supplies currency rates to `Cash` without an NYSE request; the client uses the same `Exchange` role in production and tests.  
**Episteme:** the fake is a test carrier for a limited but executable model of an external boundary.

### EOO.2.8:6 - Bias-Annotation

The **Prag** and **Trust** lenses favor behaviorally credible tests. The **Arch** lens favors interface seams. A fake itself can diverge from production and needs narrow scope.

### EOO.2.8:7 - Conformance Checklist

- Substitute through the production interface.
- Model only the behavior required by the test scenario.
- Verify outcomes, not an incidental sequence of collaborator calls.

### EOO.2.8:8 - Common Anti-Patterns and How to Avoid Them

- **Production replica:** do not rebuild the entire external service.
- **Unverified fake:** maintain contract tests or focused checks against shared expectations.

### EOO.2.8:9 - Consequences

Tests become less brittle and independent of live credentials or networks. Building a useful fake is an investment and creates another implementation to maintain.

### EOO.2.8:10 - Rationale

A fake preserves the client’s dependency role while replacing the unreliable external system with a controllable local holon. It makes the test’s evidence chain explicit.

### EOO.2.8:11 - SoTA-Echoing

Not applicable. The note retains the source’s anti-mock stance for learning; it does not claim that every kind of test double is unsuitable.
