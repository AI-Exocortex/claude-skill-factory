# Elegant Objects - Object-Oriented Design Patterns

## EOO.2.2 - Encapsulate something

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.2.2:1 - Problem frame

An object is situated by the state and collaborators it encapsulates; a class with no state can collapse into a namespace for procedures.

### EOO.2.2:2 - Problem

Stateless classes often hide static calls or direct construction inside methods, making execution and dependencies invisible to clients.

### EOO.2.2:3 - Forces

- Stateless utility code is convenient to invoke.
- An explicit collaborator gives an instance identity and makes its context substitutable.

### EOO.2.2:4 - Solution

Encapsulate at least one meaningful object or value that locates the instance in its environment. Pass a clock-like `Millis` collaborator to `Year` instead of consulting a global system clock inside `read()`.

#### EOO.2.2:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Year {
    int current() {
        return java.time.LocalDate.now().getYear();
    }
}
```

**Good**

```java
final class Year {
    private final java.time.Clock clock;

    Year(java.time.Clock clock) {
        this.clock = clock;
    }

    int current() {
        return java.time.LocalDate.now(clock).getYear();
    }
}
```

### EOO.2.2:5 - Archetypal Grounding

**System:** `Year(Millis)` represents a year relative to a specific time source; an empty `Year` silently depends on the whole environment.  
**Episteme:** the encapsulated collaborator documents the context needed to reproduce a result.

### EOO.2.2:6 - Bias-Annotation

The pattern favors **Onto/Epist** traceability and **Arch** explicit dependencies. The **Prag** lens recognizes true singleton domain entities as rare exceptions.

### EOO.2.2:7 - Conformance Checklist

- Identify each instance’s contextual state.
- Make external dependencies constructor-supplied.
- Reject stateless wrappers that merely dispatch to global procedures.

### EOO.2.2:8 - Common Anti-Patterns and How to Avoid Them

- **Empty service object:** turn the needed external capability into an encapsulated collaborator.
- **Fake state:** do not add an unused field merely to satisfy the pattern.

### EOO.2.2:9 - Consequences

Dependencies become testable and context becomes visible. Construction becomes more explicit and can expose a need for better composition at the call site.

### EOO.2.2:10 - Rationale

State distinguishes one object from another and identifies the relations in which it can act. Making that state explicit separates a represented object from a procedural façade.
