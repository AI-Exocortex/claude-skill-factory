# Elegant Objects - Object-Oriented Design Patterns

## EOO.2.7 - Write tests instead of documentation

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.2.7:1 - Problem frame

Users need trustworthy examples of what a class does, while prose documentation can drift away from executable behavior.

### EOO.2.7:2 - Problem

Comments explain intent but are not exercised when code changes; readers cannot tell whether an example still matches the implementation.

### EOO.2.7:3 - Forces

- Documentation can give broad conceptual context.
- Tests provide narrow executable examples and require maintenance to stay green.

### EOO.2.7:4 - Solution

Use concise, behavior-focused tests as the primary close-to-code explanation of how an object is constructed and used. Prefer test names and assertions that expose the contract over generalized helper tests.

#### EOO.2.7:4.1 - Bad vs. good Java examples

**Bad**

```java
/**
 * Converts dollars to cents. It is probably correct.
 */
int cents(String dollars) {
    return (int) (Double.parseDouble(dollars) * 100);
}
```

**Good**

```java
import static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.api.Test;

final class CashTest {
    @Test
    void convertsDollarTextToCents() {
        assertEquals(2995, new Cash("29.95").cents());
    }
}
```

### EOO.2.7:5 - Archetypal Grounding

**System:** a test constructs `Cash` from text and asserts its reported dollars; it demonstrates the construction contract and verifies it in the same artifact.  
**Episteme:** a passing test is executable evidence, while a comment is an unverified description.

### EOO.2.7:6 - Bias-Annotation

The **Trust** and **Did** lenses favor living examples. The **Prag** lens limits the claim: rationale, public API documentation, and operational instructions can require prose.

### EOO.2.7:7 - Conformance Checklist

- Add a readable example test for each non-obvious public behavior.
- Assert externally observable outcomes, not implementation steps.
- Keep conceptual rationale in prose where execution cannot express it.

### EOO.2.7:8 - Common Anti-Patterns and How to Avoid Them

- **Test as implementation mirror:** test a contract, not private calls.
- **Documentation replacement claim:** do not omit safety, context, or user guidance that tests cannot communicate.

### EOO.2.7:9 - Consequences

Examples become continuously checked and refactoring gets an executable safety net. Reading the full intent can require both tests and concise contextual documentation.

### EOO.2.7:10 - Rationale

The pattern raises the reliability of an explanation by connecting it to observed behavior. Its evidence remains bounded: a passing test demonstrates only the cases it exercises.

### EOO.2.7:11 - SoTA-Echoing

Not applicable. The note captures the source’s test-first documentation preference without claiming that prose is obsolete.
