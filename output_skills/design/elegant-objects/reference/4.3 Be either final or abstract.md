# Elegant Objects - Object-Oriented Design Patterns

## EOO.4.3 - Be either final or abstract

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.4.3:1 - Problem frame

Inheritance publishes whether a class is a complete black box or an incomplete design intentionally awaiting refinement.

### EOO.4.3:2 - Problem

A class that is neither final nor abstract can assume its own behavior is fixed while subclasses silently override portions of it, creating contradictory expectations.

### EOO.4.3:3 - Forces

- Open inheritance can offer reuse.
- Final classes protect complete behavior; abstract classes make incompleteness explicit and require refinement.

### EOO.4.3:4 - Solution

Make a concrete complete class final. Make an intentionally incomplete base class abstract and keep its reusable behavior final where possible. Prefer composition for variation of a complete class and reserve inheritance for refining an explicit abstraction.

#### EOO.4.3:4.1 - Bad vs. good Java examples

**Bad**

```java
class Document {
    byte[] content() {
        return new byte[0];
    }

    int length() {
        return content().length;
    }
}
```

**Good**

```java
interface Document {
    byte[] content();
}

final class FileDocument implements Document {
    public byte[] content() {
        return new byte[0];
    }
}

abstract class AbstractDocument implements Document {
    final int length() {
        return content().length;
    }
}
```

### EOO.4.3:5 - Archetypal Grounding

**System:** `DefaultDocument` is a final implementation of `Document`; `EncryptedDocument` composes it. An abstract `Document` may define final `length()` while requiring `content()`.  
**Episteme:** modifiers state whether the design is closed or intentionally partial.

### EOO.4.3:6 - Bias-Annotation

The **Arch** and **Gov** lenses favor explicit extension rights. The **Prag** lens notes language and framework constraints, especially proxying and serialization mechanisms.

### EOO.4.3:7 - Conformance Checklist

- Classify every non-interface class as complete or intentionally incomplete.
- Mark complete implementations final.
- Make extension points abstract and document their required role.

### EOO.4.3:8 - Common Anti-Patterns and How to Avoid Them

- **Accidental extension point:** do not leave classes inheritable merely by default.
- **Subclass patching:** use composition when modifying a complete object’s behavior.

### EOO.4.3:9 - Consequences

Inheritance intent becomes visible and unplanned overrides decline. Some reuse paths require explicit interfaces and decorators instead of convenient subclassing.

### EOO.4.3:10 - Rationale

A final class makes one stable behavior claim; an abstract class makes a partial claim. The mixed state blurs the boundary between a finished object and a method description awaiting completion.
