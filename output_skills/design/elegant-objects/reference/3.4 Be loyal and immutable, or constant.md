# Elegant Objects - Object-Oriented Design Patterns

## EOO.3.4 - Be loyal and immutable, or constant

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.3.4:1 - Problem frame

An object’s public identity should remain loyal to the role it was created to represent, even when it obtains different results over time.

### EOO.3.4:2 - Problem

Confusing an object’s state with values returned by its methods leads developers to call an object mutable merely because a remote or time-dependent result changes.

### EOO.3.4:3 - Forces

- Caching and live sources can change observed outputs.
- Clients need a reliable distinction between internal state change and changing facts outside the object.

### EOO.3.4:4 - Solution

Keep encapsulated state immutable and treat an object as constant in its represented role. A `Page(uri)` remains immutable when `content()` returns a different network response; it does not become a mutable page unless it changes its own state.

#### EOO.3.4:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Page {
    private String html;

    String content() {
        if (html == null) {
            html = download();
        }
        return html;
    }
}
```

**Good**

```java
final class Page {
    private final java.net.URI uri;
    private final HttpClient client;

    Page(java.net.URI uri, HttpClient client) {
        this.uri = uri;
        this.client = client;
    }

    String content() {
        return client.download(uri);
    }
}
```

### EOO.3.4:5 - Archetypal Grounding

**System:** `Cash(5)` stays five while `mul(10)` produces another cash object; `Page(uri)` stays the same page reference though the server may change.  
**Episteme:** distinguish the carrier’s state from observations about an external system.

### EOO.3.4:6 - Bias-Annotation

The **Onto/Epist** lens strongly favors the state/result distinction. The **Prag** lens requires clear documentation when an object’s method observes a changing external system.

### EOO.3.4:7 - Conformance Checklist

- Identify every field that constitutes object state.
- Verify no operation alters that state after construction.
- Document external time or I/O dependencies separately from state.

### EOO.3.4:8 - Common Anti-Patterns and How to Avoid Them

- **Output equals state:** do not infer mutation solely from changing method results.
- **Hidden cache mutation:** represent caching with a separate decorator or explicit mechanism.

### EOO.3.4:9 - Consequences

Clients can reason about identity without assuming stable external facts. The code must make time and environment dependencies visible to avoid false confidence.

### EOO.3.4:10 - Rationale

The pattern applies strict distinction: the object, its state, and a value it obtains from the world are different entities. Mixing them produces misleading claims about immutability.
