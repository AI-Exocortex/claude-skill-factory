# Elegant Objects - Object-Oriented Design Patterns

## EOO.2.6 - Be immutable

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.2.6:1 - Problem frame

Clients reason about an object through the state it represents over its lifetime.

### EOO.2.6:2 - Problem

Mutation makes an object’s identity unstable, enables partial failure and temporal coupling, complicates sharing across threads, and encourages larger stateful designs.

### EOO.2.6:3 - Forces

- Mutation can appear efficient and familiar.
- Immutable values improve local reasoning but may require persistent representations, decorators, or explicit resource strategies.

### EOO.2.6:4 - Solution

Initialize all state during construction and never modify it afterward. Operations that appear to change a value return another object. Treat identity mutability, failure atomicity, temporal coupling, `NULL` state, thread safety, and object size as consequences to audit.

#### EOO.2.6:4.1 - Bad vs. good Java examples

**Bad**

```java
final class Cash {
    private int cents;

    Cash(int cents) {
        this.cents = cents;
    }

    void multiply(int factor) {
        cents *= factor;
    }
}
```

**Good**

```java
final class Cash {
    private final int cents;

    Cash(int cents) {
        this.cents = cents;
    }

    Cash multiply(int factor) {
        return new Cash(cents * factor);
    }
}
```

### EOO.2.6:5 - Archetypal Grounding

**System:** `Cash(5).mul(10)` returns a new `Cash(50)` while the original remains five.  
**Episteme:** an immutable object is a stable carrier of the description its name and constructor supplied.

### EOO.2.6:6 - Bias-Annotation

The **Prag** and **Arch** lenses favor predictable composition and testability. The **Gov** lens favors observable invariants. The pattern has a strong bias against mutable APIs and must be weighed against external resource protocols.

### EOO.2.6:7 - Conformance Checklist

- Mark state unmodifiable where the language supports it.
- Verify each public operation leaves existing state unchanged.
- Test failed operations for absence of partial state changes.

### EOO.2.6:8 - Common Anti-Patterns and How to Avoid Them

- **Lazy mutable cache:** use an explicit decorator or language-provided memoization where possible.
- **Setter-based lifecycle:** create a new object for each meaningful state.

### EOO.2.6:9 - Consequences

Objects are safer to share, easier to test, and less temporally coupled. Allocation and explicit composition may increase, making performance evidence necessary rather than assumed.

### EOO.2.6:10 - Rationale

Stable state preserves the correspondence between an object and the claim its client holds about it. That correspondence reduces hidden history in a system of composed objects.
