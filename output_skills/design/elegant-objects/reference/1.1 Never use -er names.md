# Elegant Objects - Object-Oriented Design Patterns

## EOO.1.1 - Never use -er names

**Type:** Applied design pattern  
**Status:** Source-derived  
**Normativity:** Informative

### EOO.1.1:1 - Problem frame

In object-oriented code, a class name is the first claim about what its instances are. Names ending in `-er` or `-or` often frame an instance as a procedure holder rather than as a domain object.

### EOO.1.1:2 - Problem

`Formatter`, `Manager`, `Handler`, and similar names invite clients to command an object to manipulate data. The resulting design hides a procedural service behind a class boundary.

### EOO.1.1:3 - Forces

- A familiar activity name can be concise, but it obscures the represented entity.
- Some established nouns, such as `User` or `Computer`, are legitimate exceptions; suffix matching alone is not a rule.

### EOO.1.1:4 - Solution

Name a class for what its instances are or represent, not for an operation they perform. Rename `CashFormatter` to `Cash` or `UsdCash`; expose `usd()` as a capability. Let the object represent its encapsulated state rather than act as a connector to it.

#### EOO.1.1:4.1 - Bad vs. good Java examples

**Bad**

```java
final class CashFormatter {
    String format(int cents) {
        return "$" + cents / 100.0;
    }
}
```

**Good**

```java
final class UsdCash {
    private final int cents;

    UsdCash(int cents) {
        this.cents = cents;
    }

    String usd() {
        return "$" + cents / 100.0;
    }
}
```

### EOO.1.1:5 - Archetypal Grounding

**System:** `PrimeNumbers` is a collection-like object that exposes only prime members; it is not a `PrimeFinder` procedure.  
**Episteme:** a class name is a compact description of an object’s role and therefore shapes a reader’s model before implementation details are read.

### EOO.1.1:6 - Bias-Annotation

The pattern favors the **Onto/Epist** lens by treating names as ontological claims, and the **Did** lens by improving reading. The **Prag** lens limits it: established nouns and framework terminology require judgment.

### EOO.1.1:7 - Conformance Checklist

- Review public class names for an implied procedure holder.
- State the represented entity in one noun phrase.
- Keep operation words in capability method names, not in the class name.

### EOO.1.1:8 - Common Anti-Patterns and How to Avoid Them

- **Mechanical suffix ban:** do not rename a conventional noun merely because it ends in `-er`.
- **Cosmetic renaming:** changing `Formatter` to `Thing` without clarifying the represented entity preserves the ambiguity.

### EOO.1.1:9 - Consequences

Names steer clients toward requesting values or capabilities from objects instead of issuing procedural commands. The code may initially feel less familiar to teams accustomed to service classes.

### EOO.1.1:10 - Rationale

The source distinguishes a representative from a connector: an object stands for data and makes its own decisions about producing a result. A name that names the representative keeps that distinction visible.
